# ADR-0001: Direction of `T_A_B` and how a pose is written down

- Status: accepted
- Date: 2026-09-20
- Tags: `[ENGINEERING]`, coordinates

## Context

`docs/system-design.md` 5.2 defines composition as

```text
p_A = T_A_B @ p_B
T_A_C = T_A_B @ T_B_C
```

Two readings are possible for the sentence "`T_A_B` maps points in `B` into
`A`". If `T_A_B` is *stored as the matrix that maps B-points into A*, then the
composition rule above is valid (`T_A_C` consumes C-points and produces
A-points) — but then `T_A_C = T_A_B @ T_B_C` reads oddly, because the matrix
named "A, C" acts on C.

The trap is real and showed up during implementation: for a fixed `T_C_B`, the
"obvious" reading gives `T_B_C @ p_C = p_B`, so `T_B_C` must be
`inverse(T_C_B)`. Under the other reading `T_B_C` would be `T_C_B` itself.
Getting it backwards silently produces correct-looking code whose renders are
empty and whose projections are mirrored.

## Decision

`T_A_B` is **the pose of frame `B` expressed in frame `A`**, stored as the
homogeneous matrix that maps `B`-coordinates into `A`-coordinates:

```text
p_A = T_A_B @ p_B
```

Consequences of that single rule, all of which the code now depends on:

* `T_B_TCP = inverse(T_C_B) @ T_C_TCP` — the robot-base pose of the TCP, which
  is exactly what the IK solver needs, because `inverse(T_C_B)` consumes
  C-points and produces B-points.
* `T_E_TCP` is the TCP pose expressed in the end-effector body frame, so
  `T_B_TCP = T_B_E @ T_E_TCP` is a plain matrix product.
* `T_C_B` is the robot base pose expressed in the camera frame, which is the
  only value the renderer needs.

`ego2robot.core.frames.parse_transform_name` rejects any name that is not an
explicit `T_<frame>_<frame>` with two known frames, and
`ego2robot.core.schema.describe_pose_variable` answers "which frame to which
frame, in what unit" for any persisted array. `e2r frames` prints the registry.

## Consequences

* Every transform variable in the codebase is named by both frames; a bare
  `pose` or `transform` cross-module cannot be constructed without tripping the
  parser.
* The direction cannot be inferred from a variable name alone by a new reader,
  so `e2r frames` and the docstrings restate it at each definition site.
* `docs/system-design.md` 5.2 retains its original wording; this ADR records
  which reading is normative. A future revision of the design document should
  adopt the wording "the pose of B expressed in A".

## Evidence

* `ego2robot/core/frames.py`, `ego2robot/core/transforms.py`
* `e2r frames` output
* `tests/` is intentionally absent (AGENTS.md rule 7); the property is exercised
  instead by the five validation cases, whose ground truth is generated by
  `ego2robot.tools.hand_synth` through a different code path (direct formula
  evaluation rather than the pipeline's helpers).

## Alternatives considered

* **`T_A_B` as "maps A into B"** — rejected: it makes `T_B_TCP` mean
  "TCP expressed ... in base", which contradicts the paper's own
  `T_base^{-1} T_k^{ee}` in appendix A.4 (equation 4), where the inverse of the
  base pose is applied to an end-effector pose.
* **Sidecar metadata instead of naming** — rejected: a name that cannot be
  checked mechanically will drift.
